# Architecture and trust boundaries

## Android client

- The Compose app provides email-code onboarding, a conversation list, direct invitations by Matrix ID, contact sharing and one-to-one text conversations. A contact QR encodes an ID for exchange. Short Authentication String (SAS) comparison is the separate verification step. Compare the complete challenge with the intended person through a separate trusted channel before confirming.
- The Matrix Rust SDK pinned to Android release `26.11.05` provides Matrix sessions, sync, room encryption, decryption and device verification. A versioned interface patch exposes the SDK's existing cross-user, device-to-device SAS request; the protocol and cryptography remain in the upstream SDK. The patch requires one eligible cross-signed peer device and refuses ambiguous selection. Verification does not send room keys to an unverified contact. The app constrains its messaging flow to an encrypted direct conversation with an account on the configured service. The send guard requires an encrypted, joined conversation and a verified contact. The client configures the SDK to share keys only with trusted devices and require cross-signed sender devices for decryption. Server acknowledgment indicates that Matrix accepted an event. Delivery to a recipient and reading are separate states.
- The client stores Matrix session material in Android’s `noBackupFilesDir`. The session record uses AES-GCM with an Android Keystore key. A randomly generated key for the SDK’s encrypted store is retained in that record. The manifest disables app backup and the activity requests Android’s secure window flag. Check the platform behavior on real devices, including accessibility and recent-apps behavior. A recipient or someone controlling a device can still see what that device decrypts.
- The SDK uses the recovery key to protect private cross-signing secrets and a server-side encrypted room-key backup. The app enables recovery after the user saves and confirms the key. It holds the recovery key in memory during setup or entry and stores two encrypted flags bound to the current session and SDK store, recording readiness and whether this session recovered with the key. Copying the key is explicit, marks the clipboard item sensitive and attempts to clear that same item later.
- A returning phone needs the recovery key, a verified own device and usable SDK recovery before opening messages. Another active, cross-signed phone must sign out first. A recovered conversation shows only messages that still pass the normal sender and verified-device checks. Earlier messages can stay hidden when the original sender device can no longer be verified. Sign-out checks backup progress when recovery is set up and removes local session material after confirmed server revocation. If revocation cannot be confirmed, the app keeps the session and keys so the user can retry. The server and the other person may retain their own copies. A fresh sign-in without a saved key cannot restore a lost encrypted history.
- The application owns one SDK connection shared by its activity and optional foreground service. Background event observers subscribe independently of the selected conversation. The SDK's sync subscription set retains all verified, joined encrypted rooms alongside the current joined encrypted selection; opening or closing a conversation does not replace the background set. Alerts require a joined encrypted direct room, a currently verified peer, attested sender identity and the SDK's strict no-warning shield. They accept new text events and suppress edits and duplicate event IDs. The notification stream contains only event IDs; notification content is fixed generic text. A sync-time decryption failure may prevent an alert even if the conversation can decrypt the event later.

## Synapse and email sign-in

The Synapse module accepts a request for an email code and checks the code against a bounded, expiring challenge before issuing a short-lived Matrix login token. The Android app exchanges that token for a normal Matrix device session. The code verifies access to an email inbox. Account access and verification of the intended conversation partner are separate steps.

The challenge store uses keyed digests for email, source address and code checks. The email delivery path sees the recipient address and one-time code. The Matrix account ID is derived from a separate keyed value and has no address embedded. Rate limits and expiration reduce abuse. Mailbox compromise, an untrusted homeserver or a device compromise remain outside the protection offered by these controls.

The development fixture starts one local Synapse process with loopback HTTP and an optional authenticated synthetic mailbox endpoint. It enables the client API for a standalone test server. The development mailbox accepts only `@example.test` recipients and stores short-lived codes in its private spool. The release build embeds a required HTTPS service origin and omits the server editor. Debug loopback HTTP is for the fixture. The private deployment bundle retains PostgreSQL and server state, limits email access to an allowlist, and blocks federation; a real host, mail transport and operational verification are still required before remote use.

## Metadata and operational limits

- The homeserver can see Matrix identities, room membership, device activity, connection addresses, event timing and ciphertext sizes. Delivery providers can see email metadata. This app does not upload the phone address book or require a phone number.
- Matrix encryption aims to keep message bodies readable by participants’ devices. Its protection depends on correct SDK and server behavior, the peer identity check, devices and key handling. Local checks cover specific test cases. Independent review and device testing remain release gates.
- The alpha syncs while its process is alive. An explicit, visible-activity opt-in starts a `specialUse` foreground service with an ongoing connection notification and a stop action. Notification permission is required for that opt-in; messaging in the app remains available if permission is denied. There are no push tokens, reboot receiver, automatic service restarts or battery-policy exemptions. The server can hold an encrypted event for later sync. Device sleep, battery policy, network loss and process eviction require physical testing; background-service tests do not establish locked-device delivery.
- The alpha scope covers direct text on one active phone per account. It excludes groups, attachments, calls, public federation and subscriptions. Use fictional input while evaluating it.
